# M6.4 — conducting the proxy acceptance walk

Instructions for the Claude session that runs the walk. Written by a
prior session (2026-08-11); the user points to this file and has not
necessarily read it.

## What this is

`ROADMAP.md` M6.4: the wizard journey walked end to end by the
project's author acting the `SCOPE.md` §2 practitioner — pretending
not to know what GitHub is — from a fresh browser profile to a real
booking. Passing is the exit for 0.1.0. This document says how to
conduct it, not what the wizard does; the wizard must carry that
itself, which is precisely what is under test.

## Roles

- **Claude — UX test engineer.** Facilitate and observe. Do not
  drive, do not explain the wizard's mechanics, do not touch the
  fork, the accounts or the code while the walk runs. Every
  explanation you volunteer hides a defect the wizard has.
- **User — practitioner proxy.** They act the solo practitioner:
  competent adult, no idea what a fork, an Actions secret or a DNS
  record is. They will report their experience honestly.
- **Role switch.** If the user speaks as the project owner — most
  likely to report an apparent bug — drop the test-engineer role at
  once and return to the ordinary Claude Code role: diagnose,
  discuss, fix if asked. Log the interruption. When the matter is
  closed, ask whether to resume the walk and whether the wizard's
  state needs resetting, then re-enter the role.

## Before starting (out of role)

The wizard side of M6.4 (welcome model, phase rail, closers) landed
2026-08-11 (f0c0194); the walk needs no further building unless
findings demand it.

1. Confirm the wizard is deployed and current: the latest Deploy run
   on `parantaja-fi/openslots-caldav-appointments` is green
   (`gh run list --workflow=deploy.yml`), and no wizard commits
   postdate it — if some do, dispatch a deploy and wait for green.
   Record the commit under test in the notes file.
2. Check whether `docs/m6.4-walk-notes.md` exists. If it does, a
   walk already started and was interrupted — see resuming, below.
3. Agree the test bed with the user in a few questions: which GitHub
   account takes the fork (an existing fork or Worker may need
   removing for a fresh start — deletions are theirs to perform),
   which Cloudflare account, which calendar backend, email on or off
   and with which sender domain. Note every divergence from a true
   novice — pre-existing accounts, an already-authenticated Brevo
   domain — as limits on what this walk can prove; M6.5 keeps the
   external bar.
4. Ask them to open a fresh browser profile.

## Resuming after an interruption

A crash — of the browser, the machine, or the Claude session —
loses no walk state that matters:

- Your memory of the walk is `docs/m6.4-walk-notes.md`. Read it,
  summarise to the user where the walk stood, and ask whether to
  resume there or restart.
- The wizard's own memory lives in the browser profile's
  localStorage: the checklist, the form's knobs and the Brevo
  records survive a crash as long as the *same profile* is reopened.
  Secrets, the PAT and the Brevo key live in tab memory only and are
  pasted again — that is by design, not damage.
- Whatever already landed remotely (fork, Actions secrets, the
  deployed Worker, the Brevo domain) is real and stays; the wizard's
  probes turn the finished steps green again by themselves.
- On a restart from scratch instead: the user deletes the fork and
  the Worker, the browser profile is discarded for a fresh one, and
  the old notes file is kept — append the new attempt under a
  heading rather than erasing history.

## Conducting the walk

- Point them at
  <https://parantaja-fi.github.io/openslots-caldav-appointments/wizard/>
  and say only this much: *open this in the fresh profile and work
  through it; the page should tell you everything else.*
- Then observe. If they ask you something, answer with the smallest
  nudge that unsticks them — and record that a nudge was needed,
  what they asked, and what the page failed to convey. Being stuck
  is a finding, not a failure of the proxy.
- After each checklist step lands (or they say they are done with
  it), ask two or three short, non-leading questions — for example:
  what did you just do, in your own words? Was anything unclear or
  surprising? How confident are you that it worked? Then tell them
  to proceed.
- Keep notes as you go in `docs/m6.4-walk-notes.md` (create it at
  the first note): per step — what happened, the proxy's answers
  quoted or closely paraphrased, friction, nudges given, wait times
  that felt long, role-switch interruptions. Do not commit
  mid-walk.
- Long waits are part of the journey: the deploy run takes minutes;
  a genuinely new sender domain may park the walk on DNS
  propagation for hours. The wizard is built to resume across
  sessions — if the walk must pause, agree the resumption point and
  leave the notes file ready.
- The walk ends at the smoke step: a real booking made from the
  page, the confirmation email opened on another device, the
  booking cancelled from the email's link.

## Afterwards (out of role)

- Give a summary: verdict against the M6.4 bar, then findings
  ranked by how hard each tripped the proxy, with the proxy's own
  words where they are telling.
- Per `ROADMAP.md`, what tripped them becomes 0.1.x fixes: list the
  candidate fixes in the notes file, but change no code unasked.
- On a pass, propose the M6.4 met note for `ROADMAP.md` and the
  0.1.0 release steps; the release itself is the user's call.
- Commit the notes file (and the met note, if passing) once the
  user has seen the summary.
